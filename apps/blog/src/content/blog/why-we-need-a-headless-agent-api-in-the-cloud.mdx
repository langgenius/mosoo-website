Every generation of LLM API had a shape, and that shape defined what its generation could build.

In 2020, the Completions API was shaped like this: one string in, one string out. No roles, no conversation, no tools. The model was an expensive continuation machine, and everything else — state, memory, workflow — was yours.

In early 2023, ChatGPT's first API changed the shape: a `messages` array, with `system`, `user`, and `assistant` roles. It looked like the model had learned to hold a conversation. That was a client-side illusion — the API stayed stateless, and the "history" was something you replayed in full on every call. State was still yours.

Then came the tool-use loop of the Claude Messages API: the model returns `tool_use`, you execute the tool, you send back a `tool_result`, the model continues. This step mattered — for the first time, the model could *do* things. But notice where the loop runs: in your process. You implement the tools, you provide the environment, you gate the permissions, you handle interruption and retry.

That has been the implicit contract of API evolution these past few years: every unit of intelligence the model gains, a unit of runtime responsibility lands on you.

## The golden age of local

Claude Code and Codex supplied the half the loop was missing: a real computer. A filesystem, a shell, git, skills, MCP tools — the loop finally lived in an environment with hands and feet.

Which produced a very recognizable scene. On your laptop, you point Codex at a skill and get a repository-analysis pipeline working end to end: pull the data, run the analysis, lightly normalize the output, feed it to your own web page. The whole thing comes together in one sitting, implausibly smooth.

Smooth enough that the next thought arrives on its own: move it to the cloud, run it on a schedule, run it concurrently — or build an app on top of it for your teammates and customers.

## Then you hit the wall

Here is the problem: the Claude Messages API has no shell, and Chat Completions has no filesystem. Everything that was simply *there* on your machine does not exist in the cloud. Without a managed agent runtime, you rebuild it yourself:

- an isolated sandbox where the agent can safely run commands and write files;
- a host for a loop that runs for tens of minutes — not a serverless function that times out in thirty seconds;
- session persistence, so an interrupted task resumes instead of restarting;
- an event channel that streams intermediate progress to your frontend;
- confirmation gates for dangerous actions, file uploads and artifact downloads;
- model key custody, concurrency and queueing, usage and cost observability, recovery after failure.

Nothing on that list is your business. You set out to ship a feature and end up building an agent platform. We have watched this happen over and over: fragmented agent experiments growing on countless personal computers, all stuck at the same wall.

## The unit of compute moves again

We once wrapped tokens into an LLM API call and treated that as the smallest unit of compute. Now the unit is moving up once more: **one request to a headless agent in the cloud**.

"Headless" is the key word. Your users already have your web, your product surface — your app does not need to grow another chat window. What it needs is the agent response: hand a task to a cloud agent with a full environment, get back structured progress and results, and render them in your own pages.

Agents should be consumed the way databases are. You would not build your own Postgres replication and backups just to store a few rows; you should not build your own sandbox, loop host, and event system just to run one agent pipeline.

## Integration is a paragraph of instructions

This is what Mosoo does. A published Agent runs inside a Mosoo-managed sandbox and is exposed as a set of plain HTTP APIs: Threads, Runs, Events, Files. Create a Thread and the task begins:

```bash
curl -X POST "https://mosoo.ai/api/v1/agents/$AGENT_ID/threads" \
  -H "Authorization: Bearer $MOSOO_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "input": {
      "type": "user.message",
      "content": [
        { "type": "text", "text": "Analyze last week's commits." }
      ]
    }
  }'
```

Then poll `GET /threads/{threadId}/events`, or use `/events/stream` to stream the agent's output, tool status, and file artifacts straight into your product.

And the integration itself is not something you have to hand-write either. In the Mosoo console, every published Agent ships with an **Instruction for LLM**:

The thing you built locally with a coding agent gets wired to the cloud by the same coding agent — with no wall left for you to climb.

Agent Work that crosses the threshold should be hosted, isolated, observed, and reused like a cloud resource. This time, the distance from local to cloud is one copy-paste.
