> Follow the notes upon the journey. At first sight marks one's destiny. Return lies within the hasty keys.

数か月前、私はいくつもの顧客先を回りながら、私たちの New Agent Design in Workflow について話していました。

現場では同じ質問が繰り返されます。なぜ OpenClaw ではないのか？ Hermes Agent と何が違うのか？

少し迷子になったように感じたのは、これが初めてではありませんでした。

やがて気づきました。この混乱はどれか一つのツールの話ではなく、私たちがまだはっきり名付けていなかった一本の境界線の話だったのです。Agent Work が単なる一回の納品で終わるのはいつで、プロダクションシステムの一部になるべきなのはいつなのか？

多くのコンシューマー向けシナリオでは、前もってコンポーネントライブラリを構築するのはコストが高すぎます。

ニーズが一回きりで、同じ問題が 3 か月後にまた現れるかどうかも分からないなら、Claude Code や Codex で十分なことがほとんどです。先に抽象化する必要はありません。結果を届ける前にアプリを作る必要もありません。

問題をもっと軽く考えましょう、と顧客に伝えることさえあります。

「そんなに複雑にしなくていいんです。Claude Code で解決できます。同じ問題がまた戻ってきたら、skill を書けばいい。それが一番小さくて役に立つ投資かもしれません。」

今でもそう信じています。

けれども、もう一つのことが少しずつ見えてきました。無数の個人 PC の上で、断片化した Agent ソリューションが育ち始めていたのです。

それらは実験であると同時に、成果物でもありました。ローカル環境、Session History、コンテキスト、ファイルのコピー、MCP ツール、そして skill に依存しています。

私のコンピュータの上でなら、タスクは完了できます。あなたの環境が私のものと一致していれば、私の実験を再現することもできるでしょう。

しかし、Agent の成果物がそうやってしか移動できないのだとしたら、それは一体何なのでしょうか。消費財？ 一つの舞台の上でしか成立しないローカルな公演？

それが、私たちの旅の本当の転換点でした。

私たちは、すべての Agent Work をプラットフォームに載せようとしているわけではありません。むしろ逆です。閾値というものを尊重したいのです。

画像の世界では、グレースケールはピクセルの明暗を表します。ふつう 0 は純粋な黒、255 は純粋な白です。

Agent App にも、よく似た閾値があります。

閾値の下では、正解は一回きりのアプリ、skill、ローカルでの納品です。そこは不要な複雑さを持ち込むべきではない場所です。

閾値の上では、仕事は構築、評価、デプロイ、A/B テスト、プロダクションからのフィードバックへと変わります。ライフサイクルが必要になります。

その線を越えた途端、ツールはばらばらになります。

開発者はポイントソリューションを繋ぎ合わせることになります。サンドボックス、Eval Harness、デプロイスクリプト、ログ、権限、コンテキスト、UI。しかも実際の挙動の大半は、いまだに Prompt の文字列の中に住んでいます。

その時点で、あなたはもう Codex や Claude Code を自分の問題を解くために使ってはいません。

顧客のためのプロダクションソリューションを構築するために使っているのです。

ハーネスと依存関係の中に住み込み、ターミナルや worktree や新しい ADE を開いては、仕事をなんとか前へ進めようとします。

そのころ私は、自分に問い続けていました。なぜこの領域には、フレームワークに縛られない「Supabase」が存在しないのか？

ビルダーを置き換えるためではありません。繰り返される Agent Runtime のホスティング、デプロイ、分離、評価を、すべてのアプリから取り除くためにです。

クラウドコンピューティング以前、ソフトウェアを作ることは、土地を買い、家を建て、物件を自分で運営するようなものでした。

サーバーとスイッチとストレージを買い、マシンルームや IDC に据え付けてからでなければ、アプリケーションの話は始められませんでした。

Agent App の開発は、同じ旅を歩み始めています。

私たちはかつて、トークンを LLM API Call に包み、それを最小の計算単位として扱っていました。

いま私たちは、トークンを Cloud Agent へのリクエストに包み直そうとしています。

Hermes や OpenClaw に代表されるローカルなコンシューマー需要は、これからも続くでしょう。しかし、より複雑なプロダクション需要は、Sandbox の中の Cloud Agent へと移っていきます。

そこで必要になるのは、より高い並行性、より長く走るジョブ、より強い分離、そして作成・一時停止・再開・評価・デプロイのできるバックグラウンドタスクです。

私たちは、クラウドのマシンリソースを、開発者が直接呼び出せる Cloud Agent Session Lifecycle API へと再抽象化しています。

それが、私たちの作っているものです。

もう一つの Agent Demo ではありません。

もう一つの Prompt Wrapper でもありません。

これは一つの価値判断です。Agent Work が閾値を越えたなら、それはクラウドリソースのようにホストされ、分離され、観測され、再利用されるべきだ、という判断です。

私たちはそれを **Mosoo** と呼んでいます。

その最初のピースが、いまオープンソースになりました。Mosoo Agent Driver です。

OpenClaw、Hermes Agent、Claude Code、Codex に、互換性のある Agent Session API を話させるために私たちが使っているドライバー層です。
